# Add an approval-gated rollback workflow and rehearse it on staging

**Sprint:** S-003  **Type:** Chore  **Priority:** Medium  **Estimate:** S  **Push:** Ready  **Plan:** Pending
**Areas:** ci  **Decisions:** ADR-0005

## 1. Description
After T-034, a bad production deploy is detected but not undone. Add a manual rollback that puts the previous good Render deploy back, gated by the same `production` environment approval, and prove it on staging first. Depends on T-034 (same secrets and variables).

## 2. Business rules
None. No app behaviour changes.

## 3. Constraints
- Same constraints as T-034: free plan, no new dependency, secrets and variables per environment, names only in docs, neutral wording.
- Rollback redeploys an earlier Render deploy; it does not revert git history. Reverting the bad commit is a normal PR afterwards.
- Data on Render free resets on every deploy (ADR-0005); the runbook says so.

## 4. Acceptance criteria
- AC-1 Given a `Rollback` workflow started manually with an `environment` input (`staging` or `production`), then production rollback runs without a reviewer wait (the faster path, decided by the maintainer on 2026-10-29), while a production deploy keeps its approval (T-034). Only people with write access to the repo can start it, and the run records who did. Mechanism: the job targets a separate environment, for example `production-rollback`, which has no required reviewer and holds its own copy of the production secrets and variables; `staging` needs none.
- AC-2 Given approval, then the job finds the last successful `live` deploy before the current one, redeploys it (Render API rollback or redeploy of that commit), and polls until it is `live`.
- AC-3 Given a finished rollback, then `/health` and `/` return 200 and the run summary names the restored commit and deploy ID; otherwise the run fails.
- AC-4 Given `docs/deploy-render.md`, then it holds a rollback runbook: when to use it, how to run it, how to confirm, and the follow-up revert PR.
- AC-5 Given a staging rehearsal with two distinct deploys, then the rollback restored the earlier one, and the date, duration and outcome are recorded in the runbook.
- AC-6 `pytest` passes; no other workflow changes.

Automatic rollback on error rate, database rollback (data is disposable), branch protection, the metrics report.
