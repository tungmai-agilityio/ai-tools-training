# Add an approval-gated rollback workflow and rehearse it on staging

**Sprint:** S-003  **Type:** Chore  **Priority:** Medium  **Estimate:** S  **Push:** Ready  **Plan:** Approved
**Areas:** ci  **Decisions:** ADR-0005

## 1. Description
After T-034, a bad production deploy is detected but not undone. Add a manual rollback that puts the previous good Render deploy back, gated by the same `production` environment approval, and prove it on staging first. Depends on T-034 (same secrets and variables).

## 2. Business rules
None. No app behaviour changes.

## 3. Constraints
- Same constraints as T-034 (including the deploy hook URL as an environment secret; staging, `production-rollback` and `production` each have their own `RENDER_DEPLOY_HOOK_URL` and `APP_URL`): free plan, no new dependency, secrets and variables per environment, names only in docs, neutral wording.
- Rollback redeploys an earlier Render deploy; it does not revert git history. Reverting the bad commit is a normal PR afterwards.
- Data on Render free resets on every deploy (ADR-0005); the runbook says so.

## 4. Acceptance criteria
- AC-1 Given a `Rollback` workflow started manually with an `environment` input (`staging` or `production`), then production rollback runs without a reviewer wait (the faster path, decided by the maintainer on 2026-10-29), while a production deploy keeps its approval (T-034). Only people with write access to the repo can start it, and the run records who did. Mechanism: the job targets a separate environment, for example `production-rollback`, which has no required reviewer and holds its own copy of the production secrets and variables; `staging` needs none.
- AC-2 Given a required `ref` input (a previous release tag or commit SHA already deployed successfully), then the job calls the deploy hook with that commit and polls `/health` until it reports that commit, or fails on timeout. It rebuilds from source; it does not reuse a Render build artifact and needs no API key.
- AC-3 Given a finished rollback, then `/health` and `/` return 200 and the run summary names the restored commit and deploy ID; otherwise the run fails.
- AC-4 Given `docs/deploy-render.md`, then it holds a rollback runbook: when to use it, how to run it, how to confirm, and the follow-up revert PR.
- AC-5 Given a staging rehearsal with two distinct deploys, then the rollback restored the earlier one, and the date, duration and outcome are recorded in the runbook.
- AC-6 `pytest` passes; no other workflow changes.

## 6. Out of scope
Automatic rollback on error rate, database rollback (data is disposable), branch protection, the metrics report.

## 7. Open questions
- Answered 2026-10-29 by the maintainer: faster path for production rollback, no reviewer wait. The separate environment name and who gets write access are set at plan time.
- Answered 2026-10-29: rollback uses the same deploy hook with an earlier commit instead of Render's rollback endpoint, so no API key is needed. Slower than an artifact rollback; acceptable on the free plan.

## Plan
Approved on 2026-10-29 by the maintainer.

**Decisions:** (1) one `Rollback` workflow with an `environment` input, dispatched from `develop` (staging only allows develop, and `production-rollback` will too), so the tooling is reviewed code; (2) reuse `scripts/deploy_production.py` and add optional `DEPLOY_LABEL`, `ACTOR` and `SUMMARY_HINT` with defaults, so `deploy-production.yml` is untouched (AC-6); (3) `check_release_ref.sh` gains an optional branch argument (default `main`) — production refs must be on `main`, staging refs on `develop`; (4) `production-rollback` is a separate environment with no reviewer and its own copy of the production hook and URL, while `staging` drops its reviewer (T-036 AC-7) instead of gaining a new environment; (5) a production rollback shares the `deploy-production` concurrency group, because Render runs one deploy at a time and a concurrent hook call would only return 202 and time out.

**Steps (code, one PR):**
1. `tests/test_check_release_ref.py` first: a commit or tag on `develop` accepted for `develop`, refused for the default `main`, and an option-like branch refused; then the branch argument in `scripts/check_release_ref.sh`.
2. `tests/test_deploy_production.py` first: a rollback-style summary (title, actor, hint) plus the unchanged deploy defaults; then `DEPLOY_LABEL`, `ACTOR` and `SUMMARY_HINT` in `scripts/deploy_production.py`.
3. `.github/workflows/rollback.yml`: `workflow_dispatch` only (choice `environment`, required `ref`), `contents: read`, one job whose environment is `production-rollback` for production and `staging` otherwise, checkout `develop` with `fetch-depth: 0`, the guard with the target branch, the script, and an `if: always()` summary fallback.
4. `tests/test_rollback_config.py`: manual-only trigger, inputs, environment expression, read-only permissions, develop checkout, guard branch, one secret, actor, rollback label, and `deploy-production.yml` still targeting `production` (AC-6).
5. Docs: `docs/deploy-render.md` rollback runbook (when, how, confirm, failure, revert), the no-reviewer production path and actor, the no-op case, a rehearsal placeholder; test map updated.

**GitHub settings (maintainer):** create `production-rollback` — no required reviewer, deployment branch policy `develop`, secret `RENDER_DEPLOY_HOOK_URL` (production value), variable `APP_URL` (production URL). Remove the `staging` required reviewer and keep its `develop` policy; add staging's own `RENDER_DEPLOY_HOOK_URL` and `APP_URL` if absent. Then rehearse on staging (deploys A then B, roll back to A) and record it; a production rollback of the live commit proves the no-approval path without changing production.

**Verification:** new tests plus full `pytest`; the PR's `tests` check runs everything. Manual: TC-1/TC-2 no approval wait and the actor shown; TC-3 staging restores A; TC-4 unknown ref → hook 404 and a clear failure; TC-5 unhealthy restore → red with the manual-redeploy hint; TC-6 rehearsal recorded.
