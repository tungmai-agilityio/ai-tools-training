# Make required CI work for every PR and align merge style, AI review and Claude workflow permissions

**Sprint:** S-003  **Type:** Chore  **Priority:** High  **Estimate:** S  **Push:** Ready  **Plan:** Approved
**Areas:** ci

## 1. Description
Branch rulesets `protect-develop` and `protect-main` are active (PR, required `tests` check, linear history, no force-push, 1 approval). Four things stop them from working day to day: docs-only PRs never report `tests`, the repo merges with merge commits but linear history rejects those, nobody can approve or merge a PR in a one-maintainer team, and AI review and the Claude workflow have gaps.

## 2. Business rules
None. No app behaviour changes.

## 3. Constraints
- No new dependency; prefer plain `git diff` for the docs-only check. A pinned, well-known action only if that proves impractical.
- Settings changes in GitHub (rulesets, environments) are applied by a maintainer; the ticket lists them as steps with a check through `gh api`.
- Neutral team wording in docs.

## 4. Acceptance criteria
- AC-1 Given a PR that changes only docs, plans or markdown, then the `tests` check still reports success quickly without installing browsers or running pytest.
- AC-2 Given a PR that changes code, workflows, hooks, scripts, requirements or `render.yaml`, then the full test run still happens (the current skip list keeps its meaning).
- AC-3 Given the repo merge settings and rulesets, then only squash merge is allowed; `docs/references/git-conventions.md` and the `/pr` skill say so.
- AC-4 Given a one-maintainer team, then the maintainer is a bypass actor in pull-request mode on both rulesets, so they can merge their own PR after CI and review pass; the required approval count and other rules stay as they are.
- AC-5 Given a new push to an open non-draft PR, then `security.yml` reviews again (advisory comments only, not a required check).
- AC-6 Given `claude.yml`, then it lists allowed tools, runs only for repo members, and drops `contents: write` unless a documented step needs it.
- AC-7 Given the `staging` environment, then it has no required reviewer and keeps its branch policy for `develop`.

## Plan
Approved on 2026-10-29 by the maintainer, with the four defaults below.

**Decisions:** (1) `tests` also runs on PRs to `main`; (2) release PRs from `develop` to `main` are squash-merged too, and `git-conventions.md` notes that `main` gets commits `develop` does not; (3) the `issues: opened` trigger in `claude.yml` stays and is noted in a comment; (4) squash titles may show two numbers, `(#31) (#45)`, and the docs say so.

**Facts found:** both rulesets give the Admin role bypass mode `always`; AC-4 needs `pull_request`. A bypass also skips the required `tests` check, so "merge after CI is green" is a rule in `/pr`. The Claude app token ignores the workflow `permissions:` block, so `claude.yml` must pass `github_token`.

**Steps (code, one PR):**
1. Write `tests/test_ci_needs_tests.py` first (temp git repo, subprocess call): docs-only paths give `full=false`; code, hooks, scripts, requirements, `render.yaml`, and workflow plus docs give `full=true`; a zero SHA, an unknown SHA, an empty diff and a rename from code to docs give `full=true`.
2. Add `scripts/ci_needs_tests.sh` (plain `git diff --no-renames`; `full=false` only when every changed file is `*.md`, `docs/`, `plans/` or `.github/ISSUE_TEMPLATE/`; any doubt gives `full=true`).
3. `tests.yml`: drop both `paths-ignore` lists; triggers `pull_request` on `develop` and `main`, `push` on `develop`; keep one job with id `tests` and no `name:` or matrix; checkout with `fetch-depth: 0`; a `scope` step; every later step gated on `steps.scope.outputs.full == 'true'`; update the header comment.
4. `security.yml`: add `synchronize`; add a per-PR concurrency group with `cancel-in-progress`.
5. `claude.yml`: require owner, member or collaborator; permissions `contents: read`, `pull-requests: write`, `issues: write`, `actions: read`; drop `id-token`; pass `github_token`; read-only `--allowedTools`, with `--disallowedTools` for edits, web and `git push`; comment that it is answer-only.
6. Docs in neutral wording: `git-conventions.md` (squash only, delete branch, bypass only on one's own PR after review and green `gh pr checks`), `.claude/skills/pr/SKILL.md` (`gh pr merge --squash --delete-branch`), `.claude/skills/release/SKILL.md`, and `.claude/commands/summarize-work.md` line 19 (drop `--merges`).

**GitHub settings (maintainer, after the PR merges), then verify with `gh api`:** set both rulesets' bypass to `pull_request` and allowed methods to `["squash"]`; turn off merge commits and rebase merge in the repo; remove the `staging` environment reviewer while keeping its `develop` branch policy (always send `deployment_branch_policy` in that call, or the policy resets).

**Order:** open the PR (it runs the full suite under the new gate), squash-merge it with the current bypass, apply the settings, verify. The required-check list never changes.

**Verification:** unit tests as above. On the PR: the check is named exactly `tests`, the `scope` log prints its result, and a second push re-runs `security.yml`. After merge: the next docs-only PR shows `tests` passing in about a minute; only "Squash and merge" is offered; the rule-suites query shows `bypass`; TC-7 is verified by reading the `if` expression if no second account exists, and the PR says so.
