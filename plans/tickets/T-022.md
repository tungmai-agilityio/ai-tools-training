# Add login screen and user management to the web UI

**Sprint:** S-002  **Feature:** authentication  **Type:** Feature  **Priority:** Medium  **Estimate:** M  **Push:** Ready
**Areas:** ui  **Decisions:** ADR-0001, DDR-0001, DDR-0002, DDR-0003

## 1. Description
Working Artifacts (BA/QA edit there): [spec and test cases](https://claude.ai/artifact/Vx4CrGK2SRXTmfFyVShedS), [UI design](https://claude.ai/artifact/VaAYYy7WoVCPzw2wEwS6jp).

The web UI shows a login screen, relies on the session cookie (the UI stores no credential), shows who is signed in with a sign-out button, hides admin features from staff, and gives admins a user-management panel. Depends on the API contract of T-019, T-020 and T-023; the draft screens are in the Artifact https://claude.ai/artifact/VaAYYy7WoVCPzw2wEwS6jp (Tung to edit).

## 2. Business rules
Same role rules as T-021. A session ends at expiry (8 hours) or sign-out.

## 3. Constraints
- Change `app/static/index.html` and add `app/static/app.js`; no new dependency. No token or password in `localStorage`, `sessionStorage` or any script-readable place; requests use `credentials: "same-origin"` and the browser sends the cookie. The UI learns the signed-in user from `GET /auth/me`.
- All inline `<script>` blocks and inline event handlers move to `app.js`, so the page works under `Content-Security-Policy: script-src 'self'`.

## 4. Acceptance criteria
- AC-1 Given no session, when opening `/` (`GET /auth/me` answers 401), then only the login form is shown.
- AC-2 Given wrong credentials, then a generic error shows; given a locked account, a "try again later" message.
- AC-3 Given a successful login, then the app loads and shows the username and role.
- AC-4 Given a staff user, then holiday, time-off, revenue and user-management controls are hidden.
- AC-5 Given an admin, then the user panel lists users and can create, disable and re-enable them.
- AC-6 Given a `401` from any call, then the UI returns to the login screen.
- AC-7 Sign-out calls `POST /auth/logout`, the cookie is cleared and the login form shows.
- AC-7b Given the page under the CSP, then it loads and works with no inline script and nothing is stored in `localStorage` or `sessionStorage`.
- AC-8 Given a signed-in user, then a Change password form (current, new, confirm) is reachable from the account area and shows a success message.
- AC-9 Given an admin on the Users list, when choosing Reset password, then a dialog shows the temporary password once, with a copy button and a note that the user must change it.
- AC-10 Given a login with `must_change_password`, then only the forced Change password screen is shown until it succeeds.
- AC-11 `pytest` passes with no existing test weakened.
