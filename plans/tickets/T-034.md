# Deploy production from an approval-gated GitHub Actions workflow and verify it

**Sprint:** S-003  **Type:** Chore  **Priority:** Medium  **Estimate:** S  **Push:** Ready  **Plan:** Approved
**Areas:** ci  **Decisions:** ADR-0005

## 1. Description
Staging already redeploys from Render on every merge to `develop`. Production (`clinic-booking`) also redeploys on every push to `main`, with no approval and no check afterwards. Move production to a GitHub Actions deploy that needs an independent approval, then confirms the new deploy is healthy. Rollback is T-035.

GitHub Environments `staging` and `production` already exist. Rollback and the rehearsal are split into T-035.

## 2. Business rules
None. No app behaviour changes.

## 3. Constraints
- The deploy hook URL is a secret (the key is part of the URL): store it only as an environment secret, never echo it, regenerate it in Render if exposed. No `RENDER_API_KEY` is used.
- Render free plan; no new dependency, no paid service. Fake data only.
- Staging keeps Render auto-deploy from `develop`; do not route staging through the new workflow. The `staging` environment currently also lists a required reviewer; do not target it from a workflow without removing that.
- Secrets and variables are set in each GitHub Environment, never in the repo. Names only in docs; no values anywhere.
- The `production` environment has one required reviewer, the maintainer. Self-review prevention is off today and stays off while there is one reviewer (turning it on would block that person from approving a run they started). The approval is still a separate, recorded step in GitHub; a second reviewer would make it truly independent.
- Neutral team wording in docs.

## 4. Acceptance criteria
- AC-1 Given `render.yaml`, then `clinic-booking` has `autoDeploy: false` and `clinic-booking-stag` keeps `autoDeploy: true`. A merge to `main` creates no production deploy by itself.
- AC-2 Given a `Deploy production` workflow started manually (`workflow_dispatch`, input: a ref or tag on `main`), then its deploy job targets the `production` environment and waits for a required-reviewer approval before any step runs.
- AC-3 Given approval, then the job calls the production deploy hook with `ref=<commit SHA>` (secret URL from the `production` environment, never printed) and treats any response other than 200 or 202 as a failure.
- AC-3a Given the app, then `/health` also returns the running commit from Render's `RENDER_GIT_COMMIT` variable (`null` when unset, for example locally); the field exposes no other data.
- AC-4 Given the hook call, then the job polls `/health` until it reports the requested commit, or fails on timeout (the timeout covers a cold build and a failed build); then it calls `/` and fails unless both return 200; a failed or unhealthy result is shown in the run summary with the deploy ID and URL, and points to the rollback workflow.
- AC-5 Given the workflow, then it uses `permissions: contents: read`, no other triggers, and secrets only from the `production` environment.
- AC-6 `docs/deploy-render.md` describes the flow, the environment variables and secrets by name, who the required reviewers are, and how to read deploy status.

## 6. Out of scope
Rollback and its rehearsal (T-035); branch protection; the metrics report; changing staging; durable data or paid hosting (ADR-0005); auto-deploy on tag.

## 7. Open questions

- Answered 2026-10-29: use the deploy hook (`ref` to pick the commit) instead of an account-wide API key; status comes from `/health`. A failed build shows up as a timeout, not an explicit status. Confirm the hook behaves with `autoDeploy: false` at plan time.

Names to create (no values here): `production` environment: secret `RENDER_DEPLOY_HOOK_URL`, variable `APP_URL`. A staging check, if wanted, uses the same names in `staging`.

## Plan
Approved on 2026-10-29 by the maintainer.

**Decisions:** (1) the workflow is dispatched from `main` (the `production` environment's deployment branch policy allows only `main`) and deploys the input ref, so the tooling is always released code and an older tag never has to contain it; (2) the hook/poll/verify logic is `scripts/deploy_production.py` (stdlib only, tested against a fake Render) and the "is it on main" check is `scripts/check_release_ref.sh`, which validates the ref's shape and passes it after `--` so it cannot become a git option; (3) a commit that is already live is reported as a no-op, not as a green deploy; (4) `render.yaml` keeps `autoDeploy: false` as the AC says — Render's current equivalent is `autoDeployTrigger: off`, which takes effect on the next Blueprint sync; (5) poll timeout 20 min, job timeout 30 min, so the step summary survives a slow free-tier build.

**Facts found at plan time:** a deploy hook accepts `ref=<commit>` and answers 200 with a deploy id or 202 when another deploy is in progress; 400/401/404 are explicit failures. `RENDER_GIT_COMMIT` is set for git-backed services, which is what `/health` reports. A job-level `environment:` blocks every step until the reviewer approves.

**Steps (code, one PR):**
1. `tests/test_health.py` first: commit set and unset, exact keys, settings wiring; then `app/config.py` (`render_git_commit`, `RENDER_GIT_COMMIT`) and `app/main.py` `/health` with `commit`.
2. `tests/test_check_release_ref.py` first, then `scripts/check_release_ref.sh`: fetch `origin/main`, resolve a branch, tag (annotated tags peeled) or SHA, refuse anything not an ancestor of `origin/main`.
3. `tests/test_deploy_production.py` first (fake Render on a thread: 200/202/201/302/401, probe misses, poll, timeout, already live, unhealthy, bad env, no secret in any message), then `scripts/deploy_production.py`: trigger → pre-probe → poll `/health` for the commit → require 200 from `/` and `/health`; summary in a `finally`; no redirects; never print the URL.
4. `.github/workflows/deploy-production.yml`: only `workflow_dispatch` with a required `ref`, `permissions: contents: read`, one job on the `production` environment, checkout of the default branch with `fetch-depth: 0`, the guard step, the script step, and an `if: always()` fallback that notes a missing summary.
5. `render.yaml`: `clinic-booking` gets `autoDeploy: false`; staging untouched.
6. `tests/test_deploy_config.py`: per-service `autoDeploy` and branch, workflow triggers, read-only permissions, environment, one secret, `persist-credentials: false`.
7. Docs: `docs/deploy-render.md` (services table, production deploy flow, names and reviewers, how to read status, `/health` commit, staging vs production troubleshooting, manual rollback until T-035), `docs/references/api.md` (health body), `docs/references/testing-conventions.md` (test map).

**GitHub settings (maintainer):** the `production` environment is configured: required reviewer = the maintainer, secret `RENDER_DEPLOY_HOOK_URL`, variable `APP_URL`; the unused `RENDER_API_KEY` secret and `RENDER_SERVICE_ID` variable from the API plan are deleted. Remaining: Render → `clinic-booking` → Auto-Deploy off (confirm after the Blueprint sync). Do that before the release PR carrying `render.yaml` reaches `main`, or the sync could start an unattended deploy.

**Verification:** the new tests plus full `pytest`; on the PR the `tests` check runs everything. Manual: a dispatch waits for approval (TC-2, TC-3); an approved run is green and the summary names the commit, service URL, deploy id and both 200s (TC-4); a revoked hook fails red without printing the URL (TC-5, TC-9); a cold build keeps polling until the timeout (TC-6, covered at unit level by `test_poll_times_out_naming_the_last_commit`); a later merge to `main` creates no deploy (TC-1); the workflow holds one production secret (TC-7). Dispatching a commit that is already live reports a no-op (extra check).
