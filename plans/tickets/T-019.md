# Add cookie-based login with lockout

**Sprint:** S-002  **Feature:** authentication  **Type:** Feature  **Priority:** High  **Estimate:** M  **Push:** Ready  **Plan:** Approved
**Areas:** api  **Decisions:** ADR-0001, ADR-0002, DDR-0001

## 1. Description
Working Artifacts (BA/QA edit there): [spec and test cases](https://claude.ai/artifact/Vx4CrGK2SRXTmfFyVShedS), [UI design](https://claude.ai/artifact/VaAYYy7WoVCPzw2wEwS6jp).

Staff and admins can log in with username and password and receive an 8-hour signed session in an `HttpOnly`, `SameSite=Strict` cookie. This is the foundation; T-020, T-021, T-022 and T-023 build on it.

## 2. Business rules
Session valid 8 hours, no refresh; it lives only in the cookie. After 5 consecutive failed logins the username is locked for 15 minutes. See `plans/features/authentication/spec.md` §5 (approved by Tung as client, 2026-10-27).

## 3. Constraints
- No new dependency; stdlib hashing and HMAC. SQLite through `store`. Time via `clock.now_utc()` called through the module.
- Fails closed when `AUTH_SECRET` is unset.
- First admin: seeded at startup from `ADMIN_USERNAME` and `ADMIN_PASSWORD` only when the users table is empty. No default username or password anywhere in the repo; `.env.example` has empty placeholders. The seeded admin must change the password at first sign-in. The seed settings are read once; changing them later does not touch an existing account.

## 4. Acceptance criteria
- AC-1 Given a valid active user, when `POST /auth/login` with the right password, then `200` with username, role, `expires_at` 8 h later and `must_change_password`, and a `Set-Cookie` with `HttpOnly`, `SameSite=Strict`, `Secure`, `Path=/` and `Max-Age=28800`. The body holds no credential.
- AC-2 Given a wrong password or unknown username, when logging in, then the same generic `401`.
- AC-3 Given 5 failed logins, when the 6th attempt is made within 15 minutes (even with the right password), then `423`; after 15 minutes login works again.
- AC-4 Given a successful login, then the failure count resets.
- AC-5 Given a tampered, expired or unsigned session cookie, or `AUTH_SECRET` unset, then it is rejected.
- AC-5b Given a signed-in user, when `POST /auth/logout`, then `204` and the cookie is cleared; calling it again also gives `204`.
- AC-6 Given an empty users table and both seed variables set, when the app starts, then one admin exists with `must_change_password` true; the password is stored hashed.
- AC-6b Given an empty users table and either seed variable unset, when the app starts, then the app starts, no account is created, a warning names the missing settings, and no one can log in.
- AC-6c Given a seed password shorter than 12 characters, then startup stops with a clear error and creates no account.
- AC-6d Given users already exist, when the seed variables change or are set, then no account is created or changed.
- AC-7 `pytest` passes with no existing test weakened.
