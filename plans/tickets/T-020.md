# Let admins manage staff accounts

**Sprint:** S-002  **Feature:** authentication  **Type:** Feature  **Priority:** High  **Estimate:** S  **Push:** Ready  **Plan:** Approved
**Areas:** api  **Decisions:** ADR-0003, DDR-0001, DDR-0002

## 1. Description
Working Artifacts (BA/QA edit there): [spec and test cases](https://claude.ai/artifact/Vx4CrGK2SRXTmfFyVShedS), [UI design](https://claude.ai/artifact/VaAYYy7WoVCPzw2wEwS6jp).

Admins can list, create, disable, re-enable and change the role of staff and admin accounts. Password reset moved to T-023. Depends on T-019; can be built in parallel with T-021.

## 2. Business rules
Only admins manage users. The last active admin cannot be disabled or demoted. A disabled user's session stops working immediately.

## 3. Constraints
- Password hash never returned or logged. Failures raise `DomainError`. Admin role checked through the T-019 dependency.

## 4. Acceptance criteria
- AC-1 Given an admin session, when `POST /users` with a unique username, a valid password and a role, then `201` and the user can log in.
- AC-2 Given a duplicate username (any case), then `409`.
- AC-3 Given a password shorter than the minimum, then `422`.
- AC-4 Given an admin, when `PATCH /users/{id}` sets `active=false`, then that user's existing session gets `401` (their `session_version` is bumped).
- AC-5 Given the only active admin, when disabling or demoting them, then `409`.
- AC-6 Given a staff session, when calling any `/users` route, then `403`.
- AC-7 Re-enabling or unlocking a user clears the lockout.
- AC-8 `pytest` passes with no existing test weakened.
