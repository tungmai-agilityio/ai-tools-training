# T-011: Redesign the web app

**Status:** In Review  **Type:** Feature (Epic)  **Priority:** Low  **Reporter:** Tung Mai (dev)  **Estimate:** TBD
**Design:** https://claude.ai/artifact/QEYU98ZvzUPL9PQpDAFzw1

## 1. Summary
Redesign the clinic's web app (Book, Appointments, Today) so reception can book and manage visits in fewer steps,
and doctors can read their day at a glance on a phone. Frontend only: no API or business-rule change.

## 2. Analysis
- **Asks:** A new layout and visual design for all three screens, plus a calendar-style Today view.
- **Ambiguous:** Whether Today gets actions, and which screen opens by default (see §11).
- **First step:** Wireframe the three screens against the API we already have and get the open questions answered.

## 3. Background / problem statement
The page grew one ticket at a time (booking, list, today, reschedule in T-010) and now looks like a debug tool:
- Booking spreads its inputs across one row, and the slot list has no grouping. It is easy to book the wrong patient.
- The list mixes 4–5 same-looking action buttons per row, and Cancel uses the browser's `confirm()`.
- Today is a plain table. You cannot see at a glance who is free, who is late, or where the lunch break is.
- On a phone, the tables scroll sideways.

## 4. Goals and success metrics
| Goal | Metric (measured in the UAT walkthrough) |
|---|---|
| Faster booking | A new booking takes ≤ 4 interactions after the page loads (doctor, patient, slot, confirm) |
| Fewer mistakes | Before confirming, a summary shows patient, doctor, date/time and length |
| Day at a glance | A doctor can find their next patient on Today in under 5 s on a 375px phone |
| Usable on mobile | No horizontal page scroll at 375px on any screen |

## 5. Personas
- **Emma, receptionist.** Desktop, keyboard-heavy, books and reschedules all day.
- **Doctor.** Checks Today on a phone between patients.

## 6. User stories and acceptance criteria

**US-1 Book an appointment.** As a receptionist, I want to choose a doctor, patient, day and free slot and see a
summary before I confirm, so that I book the right visit the first time.
- AC-1.1 Given the Book screen, when I pick a doctor and a day, then free slots appear grouped into Morning and Afternoon, in clinic time.
- AC-1.2 Given I picked a slot, then the Summary shows doctor, patient (with "Insured" tag), date, time and length, and Confirm is enabled.
- AC-1.3 Given I confirm, when the API returns 201, then a success toast shows the time and the fee from the response, and the doctor and day stay selected.
- AC-1.4 Given the slot was just taken, when the API returns 409, then an error toast shows the API's `detail` and the slots reload.
- AC-1.5 Given a day with no free slots, then an empty state offers "Next open day →", which skips weekends.
- AC-1.6 The date picker cannot go before today or more than 60 days ahead.

**US-2 Reschedule.** As a receptionist, I want to move a scheduled appointment to another free slot without cancelling it.
- AC-2.1 Given a `scheduled` row, when I choose Reschedule, then Book opens in reschedule mode with a banner "Rescheduling #N, now <time>", and doctor and patient are locked.
- AC-2.2 The appointment's own current slot is offered as free (keep the T-010 `withOwnSlots` behaviour).
- AC-2.3 The Summary shows old time → new time. Confirming calls `POST /appointments/{id}/reschedule` and exits reschedule mode on success.
- AC-2.4 Cancel on the banner leaves reschedule mode with no change.

**US-3 Manage appointments.** As a receptionist, I want to filter the list and act on one appointment safely.
- AC-3.1 Status filter chips (All, Scheduled, Checked in, Completed, Cancelled, No-show, Left unseen) and a page size control. Changing either resets to page 1.
- AC-3.2 Each row shows only the actions its status allows: `scheduled` gets Check in, Reschedule, No-show, Cancel; `checked_in` gets Complete, Left unseen. The main action is a button and the rest go in a "⋯" menu.
- AC-3.3 Cancel and No-show open a `<dialog>` that names the appointment. After the action, the toast shows the fee from the API response.
- AC-3.4 Pagination shows "Page X of Y · N total". Previous and Next are disabled at the ends.
- AC-3.5 At 768px and below, rows show as cards instead of a table.

**US-4 See today at a glance.** As a doctor, I want a timeline of today's appointments per doctor.
- AC-4.1 Header shows today's date in clinic time, plus counts by status.
- AC-4.2 Timeline: one column per doctor, axis 08:00–17:00 clinic time, lunch 12:00–13:00 shaded, blocks sized by length and coloured by status with the status text visible.
- AC-4.3 A "now" line appears while the clinic is open.
- AC-4.4 A toggle switches to the list view. At 768px and below, the list is grouped by doctor.

## 7. Functional requirements
- **FR-1 Shell.** Left sidebar (name, nav, "Times in America/New_York"). At ≤ 768px it becomes a bottom tab bar.
- **FR-2 Routing.** The current screen lives in the URL hash (`#book`, `#appointments`, `#today`) and survives reload.
- **FR-3 Theme.** CSS variables on `:root` with a dark theme from `prefers-color-scheme`. Each status has one fixed colour used everywhere.
  Added on request (Tung Mai, 2026-10-16): a System / Light / Dark control at the foot of the sidebar, remembered in `localStorage`. System, the default, follows `prefers-color-scheme`.
- **FR-4 Feedback.** Toasts stack. Success hides itself; errors stay until dismissed. Lists show skeleton rows while loading, plus an empty state.
- **FR-5 Pickers.** Doctor and patient are searchable (input + filtered list or `<datalist>`).
- **FR-6 Date strip.** The next 10 clinic days (weekends skipped) plus `<input type="date">` (min today, max +60 days).

## 8. Non-functional requirements
- **NFR-1 Accessibility.** WCAG 2.1 AA: everything works with the keyboard, focus is visible, contrast is AA in both themes, nav and dialog use the correct ARIA roles, and status is never shown by colour alone.
- **NFR-2 Time zone.** Every date and time is shown in `America/New_York`, whatever the browser's time zone.
- **NFR-3 Responsive.** Works from 375px to 1440px with no horizontal page scroll.
- **NFR-4 Security.** Every API value rendered into HTML goes through `esc()`.
- **NFR-5 Performance.** No external requests other than the app's own API. The page stays one file.

## 9. Constraints and assumptions
- The design system artifact linked under **Design** above is the visual source of truth: tokens, components and screen layouts.
- Single file `app/static/index.html`, vanilla JS/CSS. No framework, CDN, build step or new dependency.
- No change to the API, business rules, fees or tests. The UI only uses: `GET /doctors`, `GET /patients`,
  `GET /doctors/{id}/slots`, `GET|POST /appointments`, `GET /appointments/today`, `GET /appointments/{id}`,
  `POST /appointments/{id}/{check-in|complete|left-unseen|no-show|cancel|reschedule}`.
- `CLINIC_TZ` stays a client-side constant (deliberately not read from the server).
- Money arrives in cents and is formatted only, never calculated.
- Assumption: opening hours and lunch are taken from `docs/business-rules.md` and hard-coded in the timeline (see §11).

## 10. Out of scope
- Any API, business-rule, fee or lifecycle change. A fee preview before confirming. The admin delete action.
- Login or roles. Doctor or patient management. Changing doctor on reschedule.
- Bugs found along the way get their own ticket.

## 11. Open questions
1. Should Today's blocks have lifecycle actions (Check in / Complete), or stay read-only as they are now?
   **Answer (Tung Mai, 2026-10-15):** Read-only. Actions stay on Appointments.
2. Which screen opens by default: Book or Today?
   **Answer:** Book.
3. Is it fine to hard-code 08:00–17:00 and the lunch hour, or should a later ticket expose the hours through the API?
   **Answer:** Hard-code them from `docs/business-rules.md`.
4. May we add an automated browser test (for example Playwright, as a dev-only dependency)? Today the repo bans new dependencies.
   **Answer:** Yes, dev-only: `requirements-dev.txt` and `tests/test_ui_browser.py`, which skips when Playwright is not installed.

## 12. Test plan
The repo has no frontend test framework, so the redesign is tested in three layers:

| Layer | How | Pass when |
|---|---|---|
| Regression | `pytest` | Green, with no test file changed |
| Functional | Manual script below, against `uvicorn` + `python scripts/seed_demo.py` | Every step matches its AC |
| Cross-cutting | Chrome DevTools: device toolbar 375px; Rendering → `prefers-color-scheme: dark`; Sensors → location/time zone `Asia/Ho_Chi_Minh`; Lighthouse → Accessibility | No sideways scroll; both themes readable; times still in New York; Lighthouse a11y ≥ 90 |

**Manual script (run in order; tick each AC):**
1. Book a 30 min and a 60 min visit (insured and uninsured patient). Check the fee in the toast against `/docs`. (AC-1.1–1.3)
2. Book the same slot in a second tab and expect the 409 detail. (AC-1.4)
3. Pick a fully booked day or a weekend date, then use "Next open day". Try to pick a date more than 60 days ahead. (AC-1.5, 1.6)
4. Reschedule a scheduled visit to its own slot, to a new day, and with a new length. Then cancel out of reschedule mode. (US-2)
5. Filter by each status, change the page size, page to the end. (AC-3.1, 3.4)
6. Run every action on suitable rows: check in, complete, left unseen, no-show (needs a past start), and cancel <24h and ≥24h; check the fee shown. (AC-3.2, 3.3)
7. Open Today on desktop and at 375px, toggle list/timeline, and check the lunch band and the now line. (US-4)
8. Use the keyboard only (Tab / Enter / Esc): book one visit and cancel one. (NFR-1)
9. Stop the server and reload: expect an error toast, no blank page. (FR-4)
